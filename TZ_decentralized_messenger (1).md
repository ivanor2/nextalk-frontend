## 1. Наименование системы

Децентрализованный веб-мессенджер **«NexTalk»***.

Под децентрализацией в рамках данного ТЗ понимается следующая модель: **авторизация и учёт пользователей** осуществляются на одном центральном сервере (сервер авторизации), а **передача сообщений** — через сеть независимых узлов (нод), развернуть и разместить которые может любой желающий по открытому протоколу/исходному коду ноды. Пользователь может пользоваться публичной нодой по умолчанию либо подключиться к своей/чужой ноде.

## 3. Назначение и цели создания системы

### 3.1 Назначение
Система предназначена для обмена текстовыми сообщениями (в перспективе — файлами и медиа) между пользователями, при этом сама передача (транзит) сообщений распределена по независимым узлам сети, а не завязана на единственный сервер заказчика — с целью повышения приватности, отказоустойчивости и устойчивости к блокировке/недоступности одного узла.

### 3.2 Цели создания
1. Разделить систему на две логически независимые части: **централизованный сервер авторизации** (учётные записи, публичные ключи, реестр доступных узлов) и **децентрализованную сеть узлов передачи сообщений**, которую может развернуть любой пользователь.
2. Минимизировать хранение содержимого переписки на любом из серверов/узлов (E2E-шифрование на клиенте — узлы видят только зашифрованные данные).
3. Обеспечить пользователю возможность выбрать узел (из общедоступных, либо свой собственный) для передачи своих сообщений.
4. Обеспечить базовые функции мессенджера: регистрация, поиск собеседника, личные и групповые чаты, статус присутствия (онлайн/офлайн).
5. Создать удобный, отзывчивый веб-интерфейс, работающий в современных браузерах без дополнительных плагинов.

### 3.3 Задачи, решаемые системой
- Единая авторизация пользователя на центральном сервере (регистрация, вход, выдача токена доступа).
- Генерация и хранение криптографических ключей на стороне клиента; связывание публичного ключа с учётной записью на сервере авторизации.
- Шифрование/дешифрование сообщений на клиенте (сквозное шифрование, E2E).
- Публикация открытого реестра узлов передачи сообщений (адрес, статус, владелец) на сервере авторизации, чтобы любой оператор мог зарегистрировать свою ноду, а клиент — выбрать, через какую ноду работать.
- Передача сообщений через выбранный пользователем узел (напрямую между двумя клиентами одного узла, либо между узлами, если собеседники используют разные ноды).
- Доставка сообщений в отсутствие собеседника онлайн (временная очередь на узле-получателе, с ограниченным сроком хранения).

## 4. Требования к системе

### 4.1 Требования к аппаратному обеспечению клиента
| Параметр | Минимальные требования |
|---|---|
| Процессор | Двухъядерный, от 1.6 ГГц |
| ОЗУ | от 4 ГБ |
| Экран | от 320 px (мобильная адаптация) |
| Подключение | Интернет от 1 Мбит/с (для голоса/видео — от 2 Мбит/с) |

### 4.2 Требования к программному обеспечению клиента
- Современный браузер с поддержкой WebSocket/WebRTC, IndexedDB, Web Crypto API: Chrome/Chromium ≥ 90, Firefox ≥ 88, Edge ≥ 90, Safari ≥ 14.
- Поддержка JavaScript (ES2020+).

### 4.3 Требования к серверной части

Серверная часть системы состоит из двух различных по роли компонентов, которые могут (и должны) разворачиваться независимо друг от друга.

#### 4.3.1 Сервер авторизации (централизованный, один на систему)
- ОС: Linux (Ubuntu Server 22.04 LTS или новее).
- Backend: **PHP 8.x** (REST API).
- СУБД: **PostgreSQL** или **MySQL**.
- Отвечает за:
  - регистрацию и вход пользователей (login/пароль);
  - хранение связки `login ↔ публичный ключ пользователя`;
  - выдачу токена доступа (напр. **JWT**, подписанного приватным ключом сервера авторизации) — токен затем предъявляется узлам передачи сообщений и проверяется ими **офлайн**, по публичному ключу сервера авторизации, без обращения к нему при каждом сообщении;
  - реестр узлов передачи сообщений: адрес узла, публичный ключ узла, владелец/контакты, статус (онлайн/офлайн), нагрузка — для того, чтобы клиент мог выбрать узел из списка;
  - поиск пользователей (по login) и получение их публичного ключа для установления чата.
- Сервер авторизации **не участвует** в передаче содержимого сообщений и не хранит переписку.
- HTTPS-соединение (TLS 1.2+) обязательно.

#### 4.3.2 Узел передачи сообщений (нода, независимый, может развернуть кто угодно)
- Распространяется как отдельное открытое серверное приложение (тот же стек — **PHP 8.x** + WebSocket-слой, напр. **Ratchet**/**Swoole**; либо long-polling как упрощённый вариант), которое любой желающий разворачивает у себя (свой хостинг/VPS).
- Отвечает за:
  - приём WebSocket-соединений от клиентов, которые выбрали данный узел;
  - проверку токена доступа клиента (выпущенного сервером авторизации) — без обращения к серверу авторизации, по его публичному ключу;
  - маршрутизацию (транзит) зашифрованных сообщений: между двумя клиентами своего узла — напрямую; между клиентами разных узлов — через узел-к-узлу соединение (нода получателя определяется по реестру узлов, который зеркалируется с сервера авторизации);
  - временное хранение зашифрованного сообщения в очереди `pending_messages` (в своей СУБД — PostgreSQL/MySQL), если получатель офлайн, с TTL (напр. 7–14 дней) и удалением после доставки/истечения срока;
  - при первом запуске — регистрацию своего адреса и публичного ключа в реестре узлов на сервере авторизации (по желанию оператора — публично, либо приватный узел без публикации, для личного/группового использования).
- Узел видит только зашифрованные blob-данные сообщений — благодаря E2E-шифрованию на клиенте содержимое переписки ему недоступно.
- Возможность запуска произвольного числа узлов одновременно, без согласования с заказчиком/владельцем сервера авторизации (кроме факта регистрации в публичном реестре, если оператор узла хочет, чтобы узел был доступен другим пользователям).

### 4.4 Требования к протоколу взаимодействия клиент/сервер-авторизации/узел
- Клиент → Сервер авторизации: регистрация, вход, получение токена, получение реестра узлов, поиск пользователя по login (получение его публичного ключа).
- Клиент → выбранный Узел: установление WebSocket-соединения, предъявление токена, отправка/получение зашифрованных сообщений, получение недоставленных сообщений из очереди.
- Узел A → Узел B (если собеседники на разных узлах): передача зашифрованного сообщения по адресу узла из реестра; аутентификация узлов друг перед другом — по публичным ключам узлов (тоже из реестра).
- Идентификатор пользователя в системе — его `login`, привязанный к публичному ключу на сервере авторизации; идентификатор узла — его публичный ключ + адрес.

### 4.5 Требования к безопасности
- End-to-end шифрование сообщений (напр. протокол на основе Double Ratchet / libsodium) — ключи не покидают устройство пользователя.
- Хранение приватных ключей только на устройстве пользователя (Web Crypto API / IndexedDB); ни сервер авторизации, ни узлы не получают приватный ключ.
- Токен доступа выдаётся сервером авторизации с ограниченным сроком действия и может быть отозван (напр. чёрный список отозванных токенов, проверяемый узлом при первом использовании токена).
- Защита от MITM при установлении соединения (проверка отпечатков ключей собеседника — «Safety numbers»), а также проверка подлинности узла (по его публичному ключу из реестра) — чтобы недобросовестный оператор узла не мог подменить маршрут.
- Защита от спама/DDoS: rate limiting на сервере авторизации и на каждом узле независимо.
- **Важно:** так как узлы передачи сообщений разворачиваются третьими лицами, оператор узла технически может видеть метаданные (кто, когда, кому отправляет сообщение через его узел, размер сообщения), но не содержимое — это должно быть явно отражено в политике конфиденциальности и доведено до пользователя при выборе узла.

### 4.6 Требования к производительности
- Установление соединения клиент → узел — не более 3 секунд при благоприятных сетевых условиях.
- Доставка текстового сообщения при обоих собеседниках онлайн на одном узле — не более 1 секунды; между разными узлами — не более 2–3 секунд.
- Одновременная поддержка не менее *(N)* активных соединений на один узел (величина фиксируется исходя из требуемой нагрузки).

### 4.7 Требования к надёжности
- Отказ сервера авторизации блокирует новые входы/регистрации, но не должен обрывать уже установленные соединения между клиентами и узлами (токен продолжает действовать до истечения срока — офлайн-проверка подписи).
- Отказ одного узла передачи сообщений не влияет на пользователей, работающих через другие узлы; пользователь может переключиться на другой узел из реестра.
- Локальное кэширование истории переписки на устройстве пользователя (офлайн-доступ к истории независимо от доступности узла).

## 6. Структура системы

### 6.1 Карта страниц
- **Главная страница (Лендинг)** — для неавторизованных пользователей.
- **Страница регистрации.**
- **Страница входа (авторизации).**
- **Личный кабинет пользователя** (список чатов, профиль, настройки).
- **Страница чата** (диалог/группа).
- **Страница поиска пользователей / добавления контакта.**
- **Страница «Узлы сети»** — список доступных публичных узлов (из реестра), выбор текущего узла, подключение своего узла по адресу.
- **Панель администратора** (сервера авторизации) — управление пользователями и реестром узлов, без доступа к содержимому переписки.

### 6.2 Главная страница
Содержит:
- Шапку (логотип, навигация, кнопки «Войти» / «Регистрация»).
- Блок с описанием концепции: единая авторизация + децентрализованная передача сообщений через узлы, которые может развернуть кто угодно.
- Блок с ключевыми функциями (E2E-шифрование, собственный/публичный узел, кроссплатформенность).
- Блок «Как это работает» (схема: сервер авторизации выдаёт токен → клиент выбирает узел → сообщения идут через узел(ы)).
- Блок «Стать оператором узла» (ссылка на инструкцию по развёртыванию своей ноды).
- Футер (контакты, ссылки на документацию/репозиторий, политика конфиденциальности).

### 6.3 Типы пользователей и их возможности

**a) Гость (неавторизованный посетитель)**
- Просмотр главной страницы.
- Регистрация нового аккаунта.
- Авторизация (вход) в существующий аккаунт.
- Просмотр списка публичных узлов (без подключения).

**b) Авторизованный пользователь**
- Просмотр и редактирование своего профиля (имя, аватар, статус).
- Выбор узла передачи сообщений: публичный из реестра по умолчанию, либо подключение собственного/стороннего узла по адресу.
- Управление списком контактов: поиск по идентификатору (login), добавление, удаление, блокировка.
- Создание личного чата с контактом.
- Создание группового чата (при наличии данной функции в MVP).
- Отправка и получение текстовых сообщений (в перспективе — файлов, голосовых сообщений).
- Просмотр статуса собеседника (онлайн/офлайн — опционально, может отключаться в настройках приватности).
- Проверка «отпечатка безопасности» ключа собеседника и подлинности используемого узла (защита от подмены).
- Управление настройками: уведомления, приватность, экспорт/импорт ключей.
- Выход из аккаунта.

**c) Оператор узла** *(не обязательно отдельная роль в системе — может быть любой пользователь, развернувший своё приложение-ноду)*
- Развёртывает приложение узла на своём сервере/VPS по инструкции.
- Регистрирует узел в публичном реестре на сервере авторизации (опционально) либо использует узел приватно (например, для своей организации/группы друзей — без публикации).
- Видит в своей административной панели узла: нагрузку, число активных соединений, объём очереди недоставленных сообщений (без доступа к содержимому).

**d) Администратор** (сервера авторизации)
- Управление реестром узлов: одобрение/удаление публичных узлов из списка (напр. при жалобах на злоупотребления), просмотр статуса.
- Блокировка учётных записей, нарушающих правила использования.
- Просмотр агрегированной, обезличенной статистики использования сервера авторизации.
- **Важно:** администратор сервера авторизации не имеет доступа к содержимому сообщений — оно передаётся через узлы в зашифрованном виде и администратору сервера авторизации не видно вообще (сервер авторизации не участвует в передаче сообщений).

### 6.4 Формы

**Форма регистрации**
Поля: имя пользователя (login), отображаемое имя, пароль (используется для локального шифрования приватного ключа, а не передаётся на сервер в открытом виде), подтверждение пароля, согласие с политикой конфиденциальности.
Действие при отправке: генерация пары ключей на клиенте → публичный ключ отправляется на сервер авторизации и привязывается к login; приватный ключ шифруется паролем и сохраняется локально (IndexedDB).

**Форма авторизации**
Поля: login, пароль.
Действие: сервер авторизации проверяет login/пароль и выдаёт токен доступа; локально расшифровывается приватный ключ; при входе с нового устройства — процедура привязки устройства/импорта ключа (QR-код, seed-фраза и т.п.).

**Форма выбора узла**
Поля: выбор из списка публичных узлов реестра (с указанием нагрузки/статуса) **или** ручной ввод адреса стороннего/собственного узла.
Действие: клиент устанавливает WebSocket-соединение с выбранным узлом, предъявляя токен, полученный от сервера авторизации.

**Форма добавления контакта**
Поля: идентификатор пользователя (login) или публичный ключ/QR-код.
Действие: запрос публичного ключа контакта у сервера авторизации → запрос на добавление в контакты, подтверждение со стороны собеседника (через его узел).

**Форма отправки сообщения**
Поля: текст сообщения, вложение (опционально).
Действие: шифрование сообщения публичным ключом получателя → отправка через текущий узел отправителя, который при необходимости пересылает его на узел получателя (или ставит в очередь, если получатель офлайн).

**Форма настроек профиля**
Поля: отображаемое имя, аватар, статус приватности (видимость онлайн-статуса), текущий узел, смена пароля, экспорт резервной копии ключей.

## 7. Требования к дизайну

### 7.1 Общий стиль
- Минималистичный, современный интерфейс в духе популярных мессенджеров (Telegram/Signal), без перегруженности элементами.
- Тёмная и светлая темы (переключение пользователем).

### 7.2 Цветовая схема
- Основной (акцентный) цвет — *(указать, например, индиго/синий #4A6CF7)*.
- Нейтральные фоны: светлый #FFFFFF / #F5F6FA, тёмный #121212 / #1A1B22.
- Цвет ошибок/предупреждений — красный/жёлтый по стандартной семантике.

### 7.3 Типографика
- Основной шрифт — без засечек (напр. Inter, Roboto, «система по умолчанию»).
- Заголовки: h1–h3 с чёткой иерархией размеров (напр. 28/22/18 px).
- Основной текст: 14–16 px, межстрочный интервал 1.4–1.6.

### 7.4 Требования к вёрстке
- Адаптивная вёрстка (Mobile First): корректное отображение от 320 px до 1920+ px.
- Сетка на базе Flexbox/CSS Grid.
- Единая библиотека UI-компонентов (кнопки, поля ввода, модальные окна, тосты-уведомления).

### 7.5 Интерактивные требования
- Мгновенное отображение отправленных/полученных сообщений без перезагрузки страницы.
- Индикатор набора текста собеседником («печатает...»).
- Индикаторы статуса сообщения (отправлено / доставлено / прочитано — при условии, что это не противоречит модели приватности).
- Индикатор текущего узла и его статуса (подключён/переподключение) в интерфейсе чата.
- Анимации переходов между экранами — плавные, не более 200–300 мс.
- Уведомления (push/in-app) о новых сообщениях.

## Примечания к использованию документа

- Поля и формулировки, отмеченные *(указать / уточнить)*, необходимо заполнить конкретными данными вашего проекта перед сдачей/защитой.
- Архитектура зафиксирована как **«один сервер авторизации + множество независимых узлов передачи сообщений»**: сервер авторизации — единая точка входа для регистрации/логина/реестра узлов, а сами сообщения идут через узлы, которые вправе развернуть любые пользователи.
- Стек: **PHP + JS**, БД **PostgreSQL или MySQL** — применяется одинаково и для сервера авторизации, и для приложения узла (это может быть один и тот же кодовый шаблон с разной ролью/конфигурацией — стоит рассмотреть на этапе проектирования, чтобы не поддерживать два разных приложения).
- Ключевой момент безопасности, который стоит явно вынести в защиту проекта: токен от сервера авторизации должен проверяться узлами **без обращения к серверу авторизации на каждое сообщение** (напр. через подпись JWT публичным ключом сервера авторизации) — иначе узлы не будут по-настоящему независимыми, а система выродится в обычную клиент-серверную архитектуру с одной лишней прослойкой.
